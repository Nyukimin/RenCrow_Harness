# RenCrow_Harness

人がCLIから使い、RenCrow_COREも作業を委譲できる共通の実行ツール。独立したGo実行プログラム`rencrow-harness`として、同じService/Kernelに対話CLI、`exec --json`、`serve --stdio`を接続する設計である。Agent・Persona・長期Memoryは持たず、受けた子Taskと作業実行履歴を所有する。モデル差の吸収はRenCrow_LLMが担う。

## 現状

設計v0.2.2は確定済み。実装は**第1段（WP04: 純粋部品）、第2段（WP04: 設定・保存・受付）、第3段a（WP04: Service・stdio・CLI・writer lock）、第3段b-1（WP04: kernelとModel実行ループ）、第3段b-2（WP04: Tool runtime）、第3段b-3（WP04: 取消・追加入力・再開）、WP05 第1段（実Model client）、WP05 第2段（act retry・clientのproduction配線）、WP06 第1段（Compactionの核と、実行中Runの自動compaction）、WP06 第2段（手動`context/compact`とdry_run、CLIの`compact`、`session/fork`、`run/resume`のcheckpoint指定、`trigger_ratio`の先行発火）、WP04 第3段c（CLIの`chat` `exec` `resume`、extension F27のAGENTS.md・SKILL読込と固定hook `before_tool` `after_tool`）、WP04 第3段d（残りの固定hook点 `before_model` `after_model` `before_compact` `after_compact` `run_terminal`と、公開前の衛生guard）、WP08 前半（`pkg/client`: CORE等が使うGoのstdio client。CORE側の配線は含まない）**まで。設計文書は[docs/](docs/README.md)に置く。

第3段b-1で足したもの: `turn/start`が受付けたRunを、Serviceに渡された**ModelPort**に対して終端まで実行する（`Admitting` → `Loading` → `Assembling` → `Measuring` → `Generating` → `ValidatingFinal` → `PersistingResult` → `Terminal`、失敗も`PersistingResult`を通って終わる）。retryはこの段では無く、WP05 第2段で加わった（下記）。ModelPortを持たないService（読取専用のcommand）は従来どおりRunを`Admitting`のまま受付だけして返し、`service/capabilities`の`turn.execution` `model.generation`はunavailable。ModelPortを持つprocess（`serve --stdio`）ではこの2つがready（basis=declared。Gatewayへ到達できるかは起動時でなくRunの開始時のdescribeで確かめる、とreasonに書く）で、`tool.runtime`とmodeごとの`tool.runtime.*`もModelPortを持つprocessでだけreadyになる（`tool.runtime.isolated`は常にunavailable）。試験用の偽物は`internal/harnesstest`にあり製品codeからは使えない。

第3段b-2で足したもの（Tool runtime）: 組込み6Tool（`file.read` `file.search` `file.create` `file.edit` `process.exec` `evidence.read`）が、Runの中で動く。act要求には、そのRunのpolicyとmodeが許すTool（`schemas/tools.schema.json`の引数schema、名前順）だけを載せる（`structured_only`は`process.exec`を載せず、載せていないToolの呼出しは応答ごと拒否する。policyが許しても書込みprefixの無い`file.create` `file.edit`、process profileの無い`process.exec`は載せない）。Modelの`tool_calls`は、**応答の全call**がTool宣言とschemaに適合した後だけ受け入れる（一つでも不正なら応答ごと`failed / MODEL_OUTPUT_INVALID`で、どのcallも実行しない）。受け入れたcallは、応答単位で一つのtransactionでActionへ束ねる（鍵は`Run + 受理したresponse ID + call ID + 応答内位置`、同じ鍵で引数hashが違えばconflict）。policyが拒否したcall（prefix外のpath、合致するprocess profile無し、未許可のenv profile）は、拒否としてActionに残り、dispatchされず、拒否の理由を答えとしてModelへ返してRunは続く。process profileが複数合致する（`POLICY_AMBIGUOUS`）のはhostの設定不良なので、Runを`blocked`で止める。callはsource順に一つずつ、dispatch-start（Thread rowのwriter epoch・control revision・policy revisionを同じtransactionで照合）→ 実行（DBのlockを持たない）→ 結果の確定（出力Evidenceのseal・答え・Attempt/Action・`action.completed`）の順で進む。成功しなかったcallがあれば、同じ応答の後続は実行せず「実行しなかった」と答える。応答のassistant messageと各答えは、バッチ末尾で一つのtransactionとして`context_entries`へ適用し（`role=tool`は`tool_call_id`一致、callの順）、次stepのpromptに載る。Runが途中で終わる時（取消・期限・効果不明）も、終端の直前に同じ適用をする。変更を許すRun（`file.create` `file.edit` `process.exec`のいずれかを載せるRun）は、workspace単位のexclusive OS lockを持つ（取れなければ`blocked / WORKSPACE_BUSY`）。Runのpolicyは開始時にdeploymentから一度だけ解決して凍結し、Threadのpolicy revisionと違えば`blocked / POLICY_CHANGED`になる。

Toolの境界: pathはworkspace相対で、実pathを一段ずつ辿って判定する（symlink・junction・reparse point、ディレクトリ上の綴りと違うcase・Unicode正規化の別名、`..`・絶対path・NUL・Windows予約名を拒否。文字列prefix検査だけで認定しない）。`file.edit`は`expected_hash`（file全体のraw bytesのSHA-256）と`old_text`の一意な完全一致を要し、同directoryの一時fileへ書いてflushし、rename直前に再hashして、原子的に置換する（rename後のdirectory flush失敗は`unknown`）。外部の非協調writerとの完全なCASは保証しない。`process.exec`は`executable`と`argv[]`を分け、shellへ連結しない。policyが許すprocess profileのうち、同じ絶対executableで`argv`の先頭がprofileの`argv_prefix`と完全一致するもの一件に解決する（0件は拒否、複数は`POLICY_AMBIGUOUS`）。子processの環境は`env_profile_ref`のvaluesだけで、hostの環境（Gateway token等）は引き継がない。出力はstdout/stderrを64 KiBごとのchunkで保存し、Runの`max_capture_bytes`に達するとprocess treeを止めて`capture_complete=false`とする。process treeの停止はLinux・macOSがprocess group、WindowsがJob Objectで、**これはsandboxではない**（`trusted_host`は子processのfilesystem・networkを隔離しない）。`isolated`は`tool.runtime.isolated`がunavailableで、別modeへfallbackしない。

crashと取消: dispatch-start後、結果の確定前にprocessが死ぬと、そのcallは`unknown`のまま残り、次のdriverがThreadを取る時に`blocked / EFFECT_OUTCOME_UNKNOWN`で終端する（同じcommandは再実行しない）。dispatch前のcallは「実行しなかった」と閉じる。processを起動したcallは、起動直後にhost incarnation・PID・開始時刻・nonceを記録し、次のdriverは、host incarnationと開始時刻が一致する生存processだけを木ごと停止する（PIDが再利用されていても無関係のprocessは止めない。照合できなければ何もしない）。cancelとdispatch-startは同じThread rowで線形化され、cancelが先ならdispatchされない。取消の受付、追加入力、`run/resume`は第3段b-3で加わった（下記）。

第3段b-3で足したもの（取消・追加入力・再開）:

- **`turn/interrupt`**: 停止信号を**記録するだけ**で、停止の完了は意味しない。Thread rowのcontrol revisionを一つ進め、`control.cancel_requested`（`reason`は固定code `USER_INTERRUPT`）とreceiptを同じtransactionで確定する。writer roleは要らない（driverを持たないprocessからも記録できる）。Runが既に終端なら`ALREADY_TERMINAL`で何も記録しない。同じkeyの再送はreceiptの答え（eventも状態変化も無し）、別keyでも既に停止要求済みのRunには二つ目の信号を作らない（`CANCEL_REQUESTED`を現revisionで返す）。expected revisionが古い要求は、停止要求済みでも`REVISION_CONFLICT`。
- **実行中workへの伝播**: Runのdriverは、記録されたcontrol変更を、(a)同じprocessなら`turn/interrupt`のcommit直後の起床（`Driver.Interrupt`）、(b)別processが記録したなら定期的なcontrol revisionの確認（既定250ms）で知り、Runのwork（describe/計数/生成/Tool/process）のcontextをcauseつきで止める。cause（`sqlite.ErrControlChanged`）でdeadlineやdriver停止と区別し、Runは`cancelled / CANCELLED`で終わる。生成中の取消は生成を`unknown`のまま残し、結果へ未解決として載せる。processは`process.Run`のprocess group／Job Objectを止め（SIGTERM→猶予→SIGKILL）、**Harnessが止めた場合だけ**、treeが空になったことを短い待ち（2秒）で確認し、確認できなければ`Uncertain`＝効果`unknown`（`blocked / EFFECT_OUTCOME_UNKNOWN`）にする（unixはprocess groupへの`kill(-pgid, 0)`、Windowsは未実機のJob Objectの`ActiveProcesses`）。
- **取消の線形化**: dispatch-startとgeneration予約に加え、**`completed`で終わるRunの`PersistTerminal`もcontrol revisionをCAS**する。取消が先にcommitされていたら最終本文は採用されず、Runは`cancelled / CANCELLED`で終わる（生成そのものの記録は変えない）。取消が後なら`ALREADY_TERMINAL`。Run開始前に記録済みの取消は、driverが開始時に読んで、何もdispatchしない。driverのいないRun（ModelPortを持たないprocess、またはdriverが終了しないまま止まったもの）は、取消が記録された時点でその場で終端する（未解決のgeneration／Toolがあればそちらが優先され、`blocked / MODEL_GENERATION_OUTCOME_UNKNOWN`か`blocked / EFFECT_OUTCOME_UNKNOWN`のまま）。
- **`input/append`**: 原本をsealed Evidenceとitemにし、queue rowを足してqueue revisionを進める。**受付は適用ではない**（contextとそのrevisionは動かない）。`next_step`は`queued`で、そのRunの次のstep冒頭（assemble）でcontextへ適用して`input.applied`を書く。`next_turn`は`queued`、`interrupt_current`は`deferred`で、同じtransactionでcontrol revisionを進めて`control.cancel_requested`（`reason`は`INPUT_INTERRUPT_CURRENT`）を別eventとして書く（停止信号を通常queueへ埋めない）。受付後に残った入力（`next_turn`、`deferred`、最終応答後に着いた`next_step`）は、**そのThreadの次のRun（`turn/start`または`run/resume`）のLoadが、受付順に、そのRun自身の入力より前に、一回だけ適用する**。Harnessが次のRunを勝手に始めることはない。対象RunがThreadのactive Runでなければ`INVALID_REQUEST`、expected control revisionが違えば`REVISION_CONFLICT`、origin proofは`turn/start`と同じ規則（nonceの再利用を拒否）で、writer roleは要らない。
- **`run/resume`**: 終端したTaskの**同じTaskに新しいRun・新しいTrace**を作る（`resume_source_run_id`、`run.started.previous_run_id`）。順序は、受付済みkeyならreceiptで答える → callerがThreadを制御できる → このprocessがThreadのwriter roleを取る（取れなければBUSY。新しく取ると、旧epochのRunが決定的に終端する）→ Taskの現状を検査（active Runが無い、`expected_last_run_id`が最後のRun、結果が`resumable`＝完了済みやrefusalは再実行しない、expected control revision、checkpointは未実装なので`UNSUPPORTED_CONTRACT`）→ Taskの**unknownのprocess Attemptをhostへ再照会**（F29。止められず動いているprocessがあれば`BUSY`で拒否して何も書かない）→ 保存済みcontextを原本に照合 → transaction（writer epoch、binding、F35のlimits）。bindingは、hostが設定したものだけをThreadへ適用し、新Runの初回からdescribeと計数をやり直す。limitsは必須で、新deadlineは受付時刻から数える。**Taskの旧Runにunknownのgenerationが残るときは、生成を始めない（fail closed）**: Runtimeへ再照会する契約が無い（下記「今も無いもの」）ので、resumeは新Run（同Task・新Trace・そのresumeのreceipt）を作り、**同じtransactionで`blocked / MODEL_GENERATION_OUTCOME_UNKNOWN`（resumable）として終端**する。結果にはunknownのgenerationのActionを未解決として載せ、Evidenceに`queried=false`で封じる。このRunはThreadのactive Runにならずdriverに渡らないので、ModelPortは一度も呼ばれない（describe・計数・生成とも）。何度resumeしても同じで、解くには、attemptの結果を照会する契約（endpointとschemaとevent）が要る。旧Runの結果・Action・Attemptは書き換えず、旧Runの消費（step・attempt・unknown）は新Runの0と別に持ち越す。同じkeyで異なるlimitsは`IDEMPOTENCY_CONFLICT`。
- **unknownは昇格しない**: effectが`unknown`のTool callは再実行せず、`completed`等にもしない。resumeがするのは**照会の記録**だけで、hostのverdict（`gone` `stopped` `unverifiable` `not_applicable`）と、unknownのまま照会できなかったgeneration（`queried=false`）を、新RunのEvidence（`resume_reconciliation`）一つに封じ、新Runの`run.started`が名指す（`evidence_id`）。`run.started`のdependencyは、旧Runの`run.terminal`（causationも）と、unknownのcallの`action.completed`。callの終端記録（`action.completed`）はAttemptごとに一つで、resumeは二つ目を書かない。新Runのpromptには、旧Runが確定した「結果は不明で、再実行していない」というToolの答えがcontextとして残る。resumeしたRunのeventのreceiptは、そのresumeのreceipt。

第3段b-3の時点で**まだ無かったもの**のうち、act retry（F31）とRenCrow_LLM clientの配線はWP05 第2段で加わった（下記）。**今も無いもの**: `Cancelling` phase（取消されたRunは`PersistingResult`から`Terminal`へ進み、phaseとしては現れない）、Windows・Ubuntuでの実機検証（Windowsの`ActiveProcesses`確認と`turn/interrupt`の経路は`GOOS=windows`のbuild・vetだけ）。model側のgenerationのunknownは**Runtimeへ再照会して解く手段が、契約のどこにも無い**ため解けない（RETRY_CONTRACT・LLM_INTEGRATION・ERROR_MAPPINGは「Runtimeの停止確認または明示再照会」と書くだけで、attemptの結果を照会するendpoint・schema・eventを定めておらず、RenCrow_LLMのGatewayにも対応するrouteが無い: `GET /v1/models` `GET /v1/status` `POST /v1/chat/completions` `POST /v1/context/measure` `/v1/embeddings` `/v1/responses`だけ）: そのTaskのresumeは上記のとおり新Runを即blockedにする（照会の契約が定まるまで緩めない。clientも作っていない）。同じThreadの別Task（`turn/start`）はこの遮断の対象ではない（契約はunknownをTaskに持たせるとだけ書き、Thread・bindingへの遮断は定めていない。設計照会中。`internal/service`の`TestAnUnknownGenerationBlocksItsTaskAndNotAnotherTaskOfTheThread`が現状を固定している）。

WP05 第1段で足したもの（実Model client）: `internal/modelclient`が`modelport.ModelPort`の唯一の実装で、RenCrow_LLMのGateway（`GET /status`のharness-v1広告とbinding descriptor、`POST /context/measure`、`POST /chat/completions`のstrict生成）へloopbackのHTTPで話す。一回の`Generate`は一回のHTTP要求で、retry・redirect・proxy・接続の再利用をしない。wireはRenCrow_LLMのfixtureとbyte一致する（`internal/modelclient`のgolden試験）。

WP05 第2段で足したもの:

- **act retry（F31）とRetryWaiting**: 通常actの一つのActionは、最初のAttempt（ordinal 0）が失敗したとき、RETRY_CONTRACT 3章の表だけを根拠に最大1回だけretryされる（純粋関数`kernel.PlanModelRetry`。時刻・DB・networkを呼ばず、nowと残予算を入力で受ける）。対象は、形式の失敗（REASONING_ONLY・EMPTY_FINAL_CONTENT・RAW_TOOL_MARKUP・MODEL_OUTPUT_SCHEMA_INVALID。生成が終わったと分かるときだけ。待ち0ms、profileは`terminal_output_once`が「Runの固定policyが許し、bindingがそのcodeに対して公開している」ときそれ、そうでなければ`same_request`）と、一時的な失敗（CONNECT_FAILED・UPSTREAM_TRANSIENT: 開始前か終了済みのとき`same_request`で1,000ms。RATE_LIMITED・QUEUE_TIMEOUT: 未開始のときだけ`same_request`で`max(1,000ms, retry_after_ms)`、10,000ms超は再送しない）。ほかは再送しない（CONTEXT_LIMIT_EXCEEDED・LENGTH/INCOMPLETE・REFUSED・BINDING_CHANGED等の契約失敗・認証・cancel・unknown・hidden retry）。2回目のAttemptの失敗は元の分類で終え、3回目は無い（DBも`model_calls.attempt_ordinal IN (0,1)`と`UNIQUE(action_id, ordinal)`で拒む）。retryできない場合（残予算0、backoffがdeadlineに届く、ほか）のRun結果は、元の失敗の終端分類のまま（`GENERATION_BUDGET_EXHAUSTED`にはしない）。
- **retryの手順**: 失敗したAttemptを確定 → `PlanModelRetry` → phase `RetryWaiting`（machineのState.Attempt=1、effect `EffWaitRetry`）→ driverが`ScheduleRetry`（fence・control revisionをCASし、retry receipt Evidenceと`model.retry_scheduled`を一transactionで書く。生成も予算消費もしない）→ backoffを実時計で待つ（Runのcontextが止まれば即座に戻る。取消は`cancelled / CANCELLED`、deadlineは`incomplete / DEADLINE_EXCEEDED`、driver停止は`incomplete / DRIVER_STOPPED`。失敗したAttemptは確定済みなのでunknownは残らず、新Attempt・新request・resetは作られない）→ `RetryDue` → 同じ適用済みContext（`Assembling`へは戻らない）にrecoveryを差し替えて**再measure**（`Measuring`）→ fit・deadline・生成回数を再判定 → `ReserveRetry`（`ReserveGeneration`と同じ規律で、writer epoch・control revision・phase・deadline・生成回数、さらにThreadのpolicy・binding revisionがRun開始時のままであることを照合し、同じActionに`attempts.ordinal=1`のAttemptと`model_calls`を足す。**model stepは数えず、generation attemptだけ消費する**。`action.prepared`は再発行せず、`action.dispatch_started` `model.attempt_started` `model.requested`を書く）→ 生成。retryの`input_digest`はprofileを含む論理入力から計算し直し、`same_request`のretryは最初のAttemptと同じ`request_digest`でなければ（`REQUEST_DIGEST_MISMATCH`）送らない。retry measureが収まらなければ`CAPACITY_BLOCKED`、未検証なら`BUDGET_UNVERIFIED`で`blocked`。backoffの終わりがdeadlineに届く場合はretryを予定せず（元の失敗の分類）、予定した後の再measureや再予約でdeadlineを跨いだ場合は`DEADLINE_EXCEEDED`で終わる。`ScheduleRetry` `ReserveRetry`はRunの固定recovery policyが許すprofileだけを受ける（driverの選択をstoreでも照合する）。`model.retry_scheduled`のevidence_idは**retry receipt**（決定・選んだprofile・fallback理由・失敗Attemptの`ModelAttemptReceipt`のID）を指し、ModelAttemptReceiptへは一段の間接参照で届く。
- **provisional切替**: retryのAttemptの予約がcommitされた直後（新Attempt IDが確定し、新streamを読む前）に`progress/reset`（old/new attempt ID、reason=trigger code）を配る。旧Attemptのprovisional本文は新Attemptの本文へ連結されない。
- **receiptの照合**: 全てのterminal（`completed`だけでなく`error` `incomplete` `refused`も）のreceiptを、request（stage・input/request digest・binding fingerprint・recovery profileとrevision・論理要求1回・hidden retryなし）と、bindingのprofileが許す変換（`applied_transformations`は公開された`transformations`の部分集合。`same_request`は無し）に照合する。食い違いは`MODEL_CONTRACT_FAILED`（receiptの申告stateは維持。retryしない）。errorのcodeがERROR_MAPPINGの表と矛盾するstateで届いた場合（例: 完了済みgenerationのRATE_LIMITED）は、frameが自己矛盾なのでstateを読めず`unknown`（`blocked / MODEL_GENERATION_OUTCOME_UNKNOWN`）にする。非2xx応答のreceiptはclientが同じ表に照合済み。
- **応答bodyのEvidence**: 非2xxの応答bodyは、先頭64 KiBまでを`StrictError.Body`に載せ、driverがそのAttemptの`model_response` Evidence（`application/json`）として封じる（超過は`capture_complete=false`）。non-streamの応答は`RawBody()`の原本をEvidenceにし、合成したstreamは保存しない。JSONでない本文（proxyのページ等）は`text/plain`、途中で切れた本文も同じ扱い。契約違反・unknownで終わったAttempt（または拒否の`source_code`があるAttempt）には、何が契約を破ったかをモデルの文面なしで書いた私有Evidence `model_attempt_diagnosis`を足す（理由が後から辿れる。何も説明するものが無いAttemptには作らない）。
- **production配線**: `serve --stdio`は、configの`gateway.base_url`（loopbackの素のhttp(s) URL）と`gateway.required_contract`（`harness-v1`）から`modelclient.Client`を起動時に組み立てて`service.Options.Model`へ渡す。契約が違う・clientが拒むURL（dot segment・空segment・escape・credential・query・非loopback・http(s)以外）は、storeに触れる前に`64`で終わる（URLは出力しない）。起動時にGatewayへは接続せず、Gatewayが居ない場合はRunが`describe`で`blocked / MODEL_UNAVAILABLE`になる。bindingはconfigの`bindings`とsession openのbindingで、未設定・不正はconfig検証で既に起動時errorである。`init` `sessions` `inspect` `evidence`はclientを組み立てない。
- **試験**: `internal/harnesstest`に、Fakeを実Gatewayの形（`GET /v1/status` `POST /v1/context/measure` `POST /v1/chat/completions`）でloopback HTTPへ出す`Gateway`を足した。`cmd/rencrow-harness`の子process試験は、実binary・実client・strict wireをこれに接続してRunを終端まで（retryを含めて）流す。

WP06 第1段で足したもの（Compaction）:

- **範囲**: 実行中のRunの**自動compaction**。起動は、actの要求のcountが**verifiedのno-fit**のときだけ（stepごとに1回。retryのAttemptでは起動しない）。`compaction.enabled=true`で、ModelPortを持つprocess（`serve`）でだけ有効（`service/capabilities`の`context.compaction`はそのときready、basis=declared）。無効なら従来どおり`blocked / CAPACITY_BLOCKED`。先行発火・手動`context/compact`・dry_run・CLIの`compact`・`session/fork`（F25）・`run/resume`のcheckpoint指定（cold resume）はWP06 第2段で加わった（下記）。
- **流れ**（`internal/compaction`。決める部分は純粋で、countと生成と読出しと記録は`Ports`越し）: Prepare（F06: 適用順のunit化、検査）→ Selection（F07/F08: 候補があるときだけ、最大1生成）→ Preflight（最小のNormal候補のverified count。no-fitならSummaryもEmergencyも無しで`CapacityBlocked`）→ Summary（F09/F10: 最大1生成）→ 候補（Normal）→ 全体のverified countでfitと縮小を判定（F13）→ commit（F14）。段のretryはしない（actの回復profileは流用しない。段の要求は`same_request`、`max_backend_attempts=1`、tool無し、`json_object`、非stream）。Normalのsemantic／model failure（出力の不正、Tool記法の混入、空・LENGTH・REFUSED等、一時的なModel失敗、段の生成予算の枯渇、Selection要求のtoken no-fit、dataset自体の上限（8 MiB・配列の長さ）の超過、候補がfitしない・縮まない）は、追加生成0の**決定的Emergency**（F12）へ進む。**Summary要求のtoken no-fit**は、仕様の「合法な投影の再構成」の手順がdocsに定義されていないため再構成せず、Summary生成0・Emergencyなしの`CapacityBlocked`（`blocked / CAPACITY_BLOCKED`、不足分を記録）で終える。strict契約・count・binding・認証が成立しない（`BUDGET_UNVERIFIED` `UNSUPPORTED_*` `BINDING_CHANGED` `AUTH_FAILED` digest不一致）場合は`unavailable`で、Runはそのcodeでblockedになる。確定した原本・checkpointの矛盾は`IntegrityBlocked`、commitの成否が分からない場合は`RestartRequired`（`restart_required / PERSISTENCE_UNCERTAIN`）。結果の写像: NormalCompacted／EmergencyCompactedは同じRunを続ける、CapacityBlocked→`blocked / CAPACITY_BLOCKED`、IntegrityBlocked→`blocked / INTEGRITY_BLOCKED`、停止→`cancelled`。
- **Selection・Summaryのdata**（STAGE_DATA）: 指示は8,000 UTF-8 byteごとに機械分割（文字の途中では内側へ戻す。連結すれば原文）、handleは各namespace（`presented` `work` `observation` `instruction` `summary` `completion`）で0始まり欠番なしで要求ごと。modelへ渡すのはhandle付きの本文だけで、hash・ID・rangeはHostのmanifestにあり、`stage`のEvidenceとして私有に保存する。除去は**quoteの完全一致（一意）**で、offsetはHostが計算し、そのquoteだけを除く。operationは一つずつ採否し（不明handle・一意でないquote・権限（Humanの指示はHumanの後続だけ、Automationの指示はHumanまたはAutomation）・順序・根拠本文との重なり・continuing_constraintは拒否）、撤回は「Aをやめて」だけで成立する（代替Bは要らない）。Summaryは前回のaccepted Summaryを最大1件、handleを除いたtextとして渡し、Observationは全体が2,048 byte以下なら全体、それ以上は先頭・末尾各1,024 byte。Summaryの検証は、提示したhandleだけ、Tool記法のtextの拒否、`passed`は成功した実行（exit code 0のprocess.execの答え、または検証済みcompletion、または前回のpassedが実行に基づく場合の継承）がある場合だけ、Workがあるのに何も言わないSummaryの拒否。completion linkは、指示が**単一fragmentで、コマンド全体をコードとして（バッククォート内か単独の行で）名指し**し、後に実行された一意のterminal process.execと双方向に一意なときだけの候補で、call_text・output_textは**それぞれ**2,048 byte以下（合計ではない）、capture完全・truncatedなし・timeout/signalなし・exit code既知。意味の完了はmodelの判断で、linkは証明ではない。
- **Emergency**（F12）: LLMを使わず、前回のSummaryとその境界、全ての指示、protected、未要約のWorkはそのまま、eligibleなObservationの答え（text・最後まで実行された呼出し・protectedでない・まだmarkerでない・原本のhashとsizeがreferenceと一致）を、(適用座標, sourceのrange開始, Evidence IDのUTF-8順, message offset)の順に**全て**、markerが元の本文よりbyteで短いときだけ置換する。置換後の候補全体のverified countで、fitと縮小（`after.upper < before.lower`、または両方exactで`after.upper < before.upper`）を判定し、bytesが減っただけでは採らない。
- **checkpoint**: 保存形式は`"rencrow-checkpoint-candidate/v1"+NUL+CJ1(candidate)`で、一度だけserializeしたbytesとそのSHA-256を保存する（設計のgoldenとbyte一致）。読み戻しは、prefix・NUL・strict JSON・CJ1再encodeの一致・schema・hash・DB行（ID・mode・parent・境界・context revision +1）の全てを要し、壊れていれば`INTEGRITY_BLOCKED`（古いcheckpointへのfallbackもcheckpointが無いものとして続けることもしない）。commit（`CommitCheckpoint`）は短い一つのtransactionで、writer epoch・Runの状態とdeadline・**control revision**（取消が先なら保存しない）・context／binding／policy revisionと現在のcheckpoint（候補作成時のまま）を照合し、sourceを原本に再照合し、checkpoint行・pointer・context revision +1・`checkpoint.committed`を一括確定する。queueへの追加だけではstaleにならない。stale（context等の変更）は保存せず、同じstepを新しいcontextから1回だけ作り直す（段の生成は`generation_attempts`に計上）。2回目は`incomplete / COMPACTION_STALE`。応答不明は発行済みのcheckpoint IDとhashで再照会する。
- **Runの中**: phaseは`Compacting` `CommittingCheckpoint`が加わった（到達可能なのは14）。段の生成はActionの`work_summary`／`instruction_selection`で、step数に数えず`generation_attempts`だけを消費する。compaction中の取消（interrupt）は生成を`unknown`のまま残し`cancelled / CANCELLED`で終わる（未解決として結果に載る）。段の生成がunknownで終わったときは、非生成のEmergencyだけを確定し、そのcheckpointを`last_checkpoint_id`としてRunは`blocked / MODEL_GENERATION_OUTCOME_UNKNOWN`で終わる（未解決の生成があるまま次のact生成をしない）。compactionの結果（status・outcome・理由・段の件数・Normalが使えなかった理由）は私有Evidence（`compaction_result` `compaction_normal_failure`）に残る。checkpointのあるThreadの次のRunは、projectionと、そのdurable boundaryより後に適用された履歴で、同じ`AssembleContext`により組み立てられる（projectionのcontext blocksは由来として保存し、組立てにはRun自身のblocksを使う）。
- **ObservationReference marker**: eligibleな答えを置き換える本文は`RENCROW_OBSERVATION_REFERENCE_V1\n`+CJ1（presentedは空・partial=true、seenとsummary_coveredは保持）。seenは、実際にgenerationを終えたact要求のcontext revision以前に適用された答えだけ（送っていない出力を既読と主張しない）。modelは`evidence.read`でEvidence IDとrangeを指定して原本（text/v1）を取り戻せる（元のToolは再実行しない）。
- **試験**: 設計のgolden（checkpoint bytes・hash、Emergencyの置換、stage messages、splitとexcerptの境界）に対する正常・拒否、Engineの五結果とA45・A24・A51、store（commitのCAS・取消が先・queueだけ・stale・応答不明・不変・source照合）、機械（phaseと遷移）、serviceのRun（Normal・Emergency・取消・unknown・Preflight・commit失敗・stale・queue・checkpointの後のRun・Selectionの適用・改ざん・無効化）、実binary・実client・strict wireのE2E。`internal/harnesstest`のGateway doubleは試験用で、製品codeからは使えない。**未実施**: 実Backendのtokenizerでの縮小の実測（A62の実token）、H10・H15・H16の品質とprefix cacheの評価、Windows・Ubuntu実機。

WP06 第2段で足したもの（手動compaction・fork・cold resume・先行発火）:

- **system Task/Run**: `AdmitCompact`が一transactionで、`kind=compaction`のTask（Turnも入力も持たない）、そのRun、受付けただけのreceipt（`operation=context/compact`、`stage=accepted`、結果なし）、`task.created`、`run.started`を作る。受付の順は`turn/start`と同じ: 同keyの既存receiptが先（応答を失ったclientの再送は、commit自体が動かした古いrevisionを持っていても同じreceiptを得る。同key・別payload（dry_runの違い・revisionの違い）は`IDEMPOTENCY_CONFLICT`）、次にcallerの制御権、active Runがあれば`BUSY`（待ちqueueへ積まない）、writer epoch、`expected_context_revision` / `expected_control_revision`（`REVISION_CONFLICT`）。limitsはcallerが渡せない（`CompactInput`に無い）ので、systemの固定値: `max_generation_attempts=min(2, host上限)`（Selection・Summaryの各1回）、`max_model_steps=1`、deadlineとcaptureはhostの上限。入力が無いRunのため、store側`loadStartRecord`を一般化した（Turnの無いTaskは「system run」で、receiptは自分の`run.started` eventのreceipt、context blocksは**同Threadの直近のturn/startのtyped blocks**（無ければ空。次のRunが運ぶblocksは起動前に分からないため、fitの判断は近似であり、本当のfitは次のRunのmeasureが決める））。`ApplyInput` / `ApplyNextSteps`はsystem Runでは何も適用しない（Threadのqueueに残る入力は次のwork Runが取る。`input/append`は受け付けるが適用はされない）。
- **driver**: 手動compactionは同じ`Driver`・同じEngine・同じ`compact`/`commitCheckpoint`で動く。機械には`Manual`状態を足した: `Admitting → Loading → Assembling → Measuring → Compacting → CommittingCheckpoint → PersistingResult`で、measureが**fitでもno-fitでも**compactionへ進む（依頼されたため）。verifiedでないcount（estimate・straddle）は`BUDGET_UNVERIFIED`でblocked。生成（act）はしない。commitが済めば`completed / COMPACTION_COMMITTED`（final messageなし、`resumable=false`、Task meaningなし）で終わる（`BuildRunResult`はsystem Runだけfinal messageなしのcompletedを許す）。stale・unknown・取消・deadlineは通常のRunと同じ扱い。`PersistTerminal`はsystem Runのcompletedで制御revisionのCASをしない（採用するfinal messageが無いため）。
- **receiptとCompactResult**: receiptは`accepted → running（driverがAdmittingを出たとき）→ terminal`。terminalの`CompactResult`は**`run.terminal`と同じtransaction**で書く（`TerminalInput.CompactResult`。systemのcompaction Runにだけ必須で、他のRunへ渡すと拒否）。写像（`kernel.BuildCompactResult`、純粋）: checkpointをcommitした→`executed`＋`NormalCompacted` / `EmergencyCompacted`、checkpoint ID・before/after（verified）・両boundary（unknown generationが残るときだけ`error`も付く）、`CAPACITY_BLOCKED`→`executed / CapacityBlocked`（不足が実在するときだけ`required_minimum_tokens` / `available_tokens`を対で）、`INTEGRITY_BLOCKED`→`executed / IntegrityBlocked`、commit不明→`executed / RestartRequired`（checkpoint IDは返さない）、取消・deadline・driver停止→`cancelled`、二度のstale→`stale`、それ以外（`BUDGET_UNVERIFIED` `MODEL_UNAVAILABLE` `UNSUPPORTED_*` unknown generation等）→`unavailable`＋code。driverがいなくなったsystem Runは、次のdriverが`settle`で終端し、receiptも同じtransactionでterminalにする（checkpointが残っていればそれを`executed`として、無ければ`cancelled`）。応答を失った再問い合わせ（A07）は、同keyで同receiptを得る。commitの成否不明は第1段の`ResolveCheckpoint`（発行済みIDとhash）で決まり、決まらなければ`RestartRequired`。
- **dry_run**: `AdmitCompactDryRun`が**receipt一行だけ**を保存する（terminal、`CompactResult{status: dry_run, outcome: null, checkpoint_id: null, before: 現在のpromptのverified count, after: null}`）。Task・Run・Evidence・event・checkpointを作らず、context・control revisionを動かさず、生成せず（describeとmeasureだけ）、busyなThreadでも受ける。`required_minimum_tokens` / `available_tokens`は`CapacityBlocked`の結果にしか付けられない（`CompactResult.Validate`）ので、dry_runは返さない。countが検証できない・bindingがstrictでない・保存されたcontextが読み戻せないは`status=unavailable`（`executed`の結果に偽装しない）。このprocessにModelPortが無い、または`compaction.enabled=false`のときは、dry_runも`UNSUPPORTED_CONTRACT`（capabilityの理由そのままで、何も書かない）。
- **CLI `compact`**: `compact --config ABS --thread ID [--dry-run] [--idempotency-key KEY]`。Threadの現在のrevisionでServiceへ依頼し、receiptのterminalを待って、`CompactResult`を標準出力へ一つのcanonical JSONとして出す（人向けの一行は標準error）。checkpointを作った・dry_runが答えたなら終了code 0、それ以外の終わり（`CapacityBlocked`等）や拒否は1、command lineの誤りは64（2〜6はexecのRun結果用で使わない）。Ctrl-Cは対象Runの停止を一度記録して終わるのを待つ。keyを省略すると毎回別の操作になり、与えて再実行すると、revisionが動いていれば別payloadとして`IDEMPOTENCY_CONFLICT`になる。
- **`session/fork`（F25）**: 同じSessionに新しいThreadを作る（ACLはsourceと同じ。callerはsourceを制御できること）。`AdmitFork`が一transactionで、Thread（`source_thread_id`、writer epoch 1、context revision 1）、`session_maintenance`のTaskと即completedのRun（`SESSION_FORKED`、Task meaningなし）、**`mode=fork`のcheckpoint**（sourceのcheckpointのprojection・boundary・inventory・retained refs・snapshot digestをそのままコピー、parentなし、`expected`は新Threadのcommit前の値）、provenanceの**import**、receipt（`ForkResult`）、event五つ（`session.created` `task.created` `run.started` `checkpoint.committed` `run.terminal`）を作る。sourceには何もcommitせず、sourceのsnapshotを動かさない。sourceがbusy（active RunやTool実行中）でも受ける（checkpointは不変で、実行中のeffect・Tool状態・queue・itemは何もコピーしない）。fileは巻き戻さない。count: `before_count`はsourceのafter_count、`after_count`は、新Threadのbinding（sourceと同じ）のdescriptorのfingerprintとコピーのact要求の論理input digestがsourceのcountの両者と**一致するときだけそのcountを引き継ぎ**（modelへは何も尋ねない）、違えば新しくmeasureする。verifiedでなければ`BUDGET_UNVERIFIED`、収まらなければ`INVALID_REQUEST`で、何も書かない。forkはno-shrinkの対象ではない。ModelPortが無いprocessは`UNSUPPORTED_CONTRACT`。
- **provenance import**: コピーが名指すsource（entry・selection・Summaryのsource map・保持reference・Observation inventoryのEvidenceと、Summaryを採用したcheckpoint）を、**source Threadの出所の中で**transaction内で再照合し、新Threadが`source_imports`へimportする。以後、新Threadが読める（`evidence.read` Tool、compactionの`ReadText`）・名指せる（commit時の`verifySources`）のは、自分のものとimportしたものだけ。fork後にsourceが進めた分は読めない。forkのforkも、importの鎖ではなくそのcheckpointが名指すものをimportする。新Threadの`context_seq`は、現checkpointのdurable boundaryより後から始まる（schemaのtriggerと、三箇所のINSERTの共通式`insertContextEntry`で）。
- **cold resume（`run/resume`のcheckpoint指定）**: `ResumeInput.checkpoint_id`は、Threadが**現に立っているcheckpoint**（nullなら現checkpoint、無ければnull）でなければ`REVISION_CONFLICT`（巻戻しはしない。古いcheckpointから作業するのはforkである）。Serviceはadmissionの前（hostへ未確定のcallを照会するより前）に`kernel.VerifyStanding`で、Threadのsnapshot（適用済みtextとtyped blockのhash・digest・revision）、checkpointのprefix・NUL・strict JSON・CJ1再encodeの一致・schema・hash、DB行（ID・mode・parent・両boundary・context revision）、Summaryを採用したcheckpoint（自分のものかimport済み）、context全体の整合（`compaction.Prepare`）、checkpointが名指す全source（inventoryのObservation含む。存在・sealed・hash欄・長さ）を読み戻す。一つでも合わなければ`INTEGRITY_BLOCKED`で受付けず、Run・receipt・eventを作らない。古いcheckpointへfallbackせず、checkpointが無いものとも読まない。admissionのtransactionは、検証したcheckpointがまだ現checkpointであることを再度fenceする。`ResumeResult.checkpoint_id`は、そのRunが立つcheckpoint。sourceの**bytes（chunk）の再hash**はしない（存在・sealed・記録されたhash欄・長さの照合で、applied textとtyped blockは読み戻してhashを検証する）。
- **`trigger_ratio`**: actのmeasureが**verifiedのfit**で、`upper * 10^6 >= round(ratio * 10^6) * usable`（境界を含む。整数比較で、floatの積は使わない。`contextplan.ReachesTrigger`）のとき、そのstepの最初のAttemptだけ、promptがfullになる前にcompactionを起動する。起動した先行compactionがcheckpointを作れなかったとき（Summary要求がno-fit・countが検証できない・candidateがstale・一時的なModel失敗後のEmergencyもno-fit等）は**Runを止めず**、measureしたprompt（fitしている）でそのまま生成へ進む（`EvCompactSkipped`。stageが使った生成attemptは数える）。**そのRunでは先行発火を二度試さない**（`EarlyTried`）。fitしなくなったpromptの通常のcompactionは従来どおり。取消・store失敗・読み戻せない保存状態・unknown generationは従来どおりRunを終える。checkpointをcommitしたら、stepを組み直して数え直す（古いcountを使わない）。ratioが(0,1)の外（手組みのdriver）なら先行発火しない。
- **DDL（`migrations/001_initial.sql`への最小追加。既存の定義は変えていない）**: 表`source_imports`（PK `(thread_id, source_kind, source_id)`、`source_kind`は`evidence` / `checkpoint`、`from_thread_id` `from_checkpoint_id` `fork_checkpoint_id`、変更・削除はtriggerで拒否）と、`context_entries`のBEFORE INSERT trigger（現checkpointのdurable boundary以前の適用を拒否）。**schema versionは1のまま**で、`Open`はこれらが無いstore（この版より前のbuildの使い捨てdraft store）を`ErrSchemaOutdated`で拒否する（変換しない。draftのDDLは明示再初期化が前提）。restore closureは`source_imports`の参照も検査する。
- **試験**: manual（A06 A07 A17 A60の手動経路、dry_run、BUSY・REVISION_CONFLICT・FORBIDDEN、実行中の入力のappend、取消、Emergency / CapacityBlocked / unavailable、commitの応答消失・不発、driver死後の終端）、fork（A36、provenance、busyなsource、拒否、count、fork先のNormal・Emergency compaction、import無しの拒否）、cold resume（H03 H11 H26: 12通りの改ざんと、古いcheckpointへのfallback拒否）、trigger_ratio（境界・skip・一度だけ・hard path・unknown）、機械（Manual・Early・skip・stale）、store（admission・receipt・terminal・trigger・Open・closure）、実binary・実client・strict wireのCLI `compact`。**未実施**: 実Backendのtokenizerでの受入、H10 H15 H16の品質、Windows・Ubuntu実機（CLIの`chat` `exec` `resume`とhook（F27）はWP04 第3段cで加わった。下記）。

WP04 第3段cで足したもの（CLIの`chat` `exec` `resume`、extension F27、Run開始時のcheckpoint source検証）:

- **三つのCLIに共通**: `compact`と同じく、このprocessがServiceを組み立て（writer roleとGateway clientを持つ）、Runを自分で駆動する。入力のentrypointは`chat`が`cli_interactive`、`exec`と`resume`が`cli_exec`。標準入力がterminalかどうかで由来を決めない。originは、`exec --origin human|automation|unknown`の明示宣言をprofileの`default_origin`で頭打ちにしたもの（既定はautomation）、`chat`の行は`declared_local`のhuman（profileがhumanを許すとき）。本人の証明ではない。`--binding`はconfigの`bindings[].profile_name`、`--workspace`はclean形の絶対pathで実pathがconfigのworkspaceと完全一致するもの。session modeの既定は`structured_only`で、`--mode`で明示する。Runのlimitsは、そのsessionのpolicyとhostの上限の小さい方（`EffectiveCaps`）を全項目送る。
- **`exec`**: `exec --config ABS --workspace ABS --binding PROFILE --input-file ABS [--json] [--mode MODE] [--origin ORIGIN] [--idempotency-key KEY]`。新しいsessionに一つのturnを置き、入力は`--input-file`の本文（標準入力は読まない。8 MiB以下のUTF-8、空でない）。`--json`では標準出力がJSON linesだけ（`{"type":"event","event":Event}`をThreadの最初のevent（`session.created`）からRunの`run.terminal`までcommit順に、最後に`{"type":"result","result":RunResult}`）。`--json`なしでは標準出力にfinal textだけ、標準errorに人向けの短い行。**終了code**はPROTOCOL§2のとおり: completed=0、incomplete=2、rejected・blocked=3、cancelled=4、failed=5、restart_required=6、command line・config・値の不正=64、Runを始めなかった操作の失敗（未初期化・busy・拒否）=1。0はRunの終わりで、Taskの達成ではない（resultのverificationを読む）。Ctrl-C（SIGINT）とSIGTERMは停止を**一度だけ記録**し（`turn/interrupt`）、最大30秒Runの終わりを待つ。記録しただけでcancelledとは扱わない。`--idempotency-key`を与えて再実行すると、session・turnとも同じ受付になり、最初のRunのstreamとresultが返る（生成し直さない。その後resumeされたRunのeventは混ざらない）。
- **event streamの順序**: `exec` `resume`は、eventをServiceの通知からではなく、storeから`events/read`（after_seq）で順に読んで出す（通知は起床にだけ使う）。`turn/interrupt`の戻りのevent（`control.cancel_requested`）と、駆動側が直後にcommitして通知する`run.terminal`は別の経路で、互いに追い越しうるため。Runが終端と分かった後にもう一度読み切ってからresultを書く。`resume`のstreamは新しいRunのeventだけ。
- **`resume`**: `resume --config ABS --task TASK_ID --last-run RUN_ID [--json] [--idempotency-key KEY]`。同じTaskの新しいRunを`run/resume`で受け付け、`exec`と同じ出力・終了codeで終端まで駆動する。`--last-run`はそのTaskのRunであること（違えば64、Taskの最後のRunでなければServiceが拒否）。limitsは前のRunのlimitsを、sessionのpolicyとhostの**現在の上限へ頭打ち**にして全項目を送る（下げたら標準errorに書く。新しいdeadlineは受付時から）。checkpointはThreadが立っているもの、bindingは前のまま、control revisionは直前に読んだThreadの値。
- **`chat`**: `chat --config ABS --workspace ABS --binding PROFILE [--mode MODE]`。起動のたびに新しいsessionを作り、標準入力の行を読む。モデルの本文はstreamしながら標準出力へ、それ以外（prompt・eventの短い行・コマンドへの答え）は標準errorへ。Runが無いとき普通の行は新しいturn（`turn/start`）、あるときは同じRunへの追加入力（`next_step`）。`/interrupt <text>`は`interrupt_current`、`/later <text>`は`next_turn`、`/stop`とCtrl-Cは`turn/interrupt`（記録だけ。Runが終わったら「ended」と表示）、`/compact`はRunが無いときだけ（あれば拒否し、queueしない）、`/status`、`/exit`、`//text`（先頭が`/`の本文）、`/help`。**`/interrupt`は次のRunを自分では始めない**: textはdeferredとしてThreadに保持され、次のturnのLoadが本文より前に適用する（表示にもそう出る）。`/later`と`/interrupt`は、Runが無い・終わっていたときは何も記録せずに知らせる（別種の入力として送り直さない）。普通の行が、Runが終わる瞬間に来たときは、Runの状態を見て新しいturnとして送る（捨てない。標準errorに出る）。signalと行とRunの終了通知は、一つのmain loopだけが状態を判定する。Ctrl-Cは、Runがあり停止が未記録なら停止を記録、Runが無い・記録済みなら終了。二度目のCtrl-Cは待たずに終了（Runは終了処理で停止され、終了code 4）。標準入力のEOFは**cancel相当**（PROTOCOL§2）: Runがあれば停止を記録して終わりを待ち、そのRunの終わり方の終了code（cancelledなら4。待ちきれなければ1）、無ければ0。`/exit`で止めたRunも同じ。

- **context取消**: requestをwriterへ渡す前にcontextが終われば未送信（ctxのerrorだけ）。渡した後なら`ErrOutcomeUnknown`も含み、**同じidempotency keyと同じpayloadで再送する**（Harnessがreceiptから答える）。遅れて届いたresponseは読んで捨てる。contextはRunを暗黙に止めない。止めるのは明示の`TurnInterrupt` / `InterruptRun`（`run/get`のcontrol revisionを読み、keyは`prefix.r<revision>`、REVISION_CONFLICTは3回まで）、または`AwaitRun`の`InterruptKeyPrefix`（contextが先に終わったら停止信号を1回記録し、`CancelGrace`の間Runの終端を待つ）。`AwaitRun`は`run.terminal`通知を待ち、安全網の低頻度pollでも見る（別processが駆動するRun向け）。返す`RunResult`は`run/get`の値で、`completed`をTaskの成功とは扱わない（`Verification`を読む）。
- **通知**: `Notifications()`は確定event・progress（delta/reset/gap）をHarnessが送った順に返す。readerはconsumerを待たないので、遅いconsumerがresponseや取消を詰まらせない。上限（`Config.Notifications`）を超えたprogressは`LocalGap`付きのgapに畳み、**確定eventは決して捨てず**、保てなければ接続を`ErrNotificationOverflow`で閉じる（`EventsRead`で取り直す）。直近8192件のevent_idの重複は捨てる。通知を使わない呼出し側は`IgnoreNotifications`。
- **二段階停止**: `Abort()`は即時（新規呼出しを拒否し、待つ呼出しを失敗させ、通知を捨て、子processをkillして回収を待つ）。`Shutdown(ctx, ShutdownInput)`は後段の穏当な停止（新規呼出しを拒否し、`service/shutdown`を送り、exitを待つ。`2×deadline + ExitGrace`で出なければkillして`ErrShutdownTimeout`）。どちらも冪等・並行安全で、`Done()`は子processが消えてから閉じる（子が消えた後も孫processがstdoutのpipeを保持している場合は、短い猶予の後に読取側を閉じて待たない）。`Abort`は、正常終了後に通知を読み切らなかったconsumerの解放にも使える。`Abort`はHarnessに何も頼まないので、駆動中のRunはstore上で非終端のまま次のprocessが終端させる（Tool processの停止はHarness側の責務で、このclientはprocess groupを扱わない）。
- **最小の使い方**:

```go
c, err := client.Start(ctx, client.Config{
	Binary: "/abs/rencrow-harness", ConfigPath: "/abs/harness-config.json", Dir: "/abs/work",
	ClientName: "my-caller", ClientVersion: "1", // Env nil: the child gets an empty environment
})
if err != nil { /* ErrIncompatible, ErrInvalidConfig, ... */ }
defer c.Abort() // a no-op after a clean Shutdown
go func() { for n := range c.Notifications() { _ = n } }() // read until it is closed

open, _ := c.SessionOpen(ctx, protocol.SessionOpenInput{ /* workspace, binding, policy, mode, key */ })
start, _ := c.TurnStart(ctx, protocol.StartInput{ThreadID: open.Session.ThreadID /* ... */})
res, err := c.AwaitRun(ctx, start.RunID, client.AwaitOptions{InterruptKeyPrefix: "stop." + start.RunID})
_ = c.Shutdown(ctx, protocol.ShutdownInput{Mode: "drain", DeadlineSeconds: 10})
```

- **試験**: `pkg/client`の単体（framing・envelope・response対応・context・protocol違反16種・通知の順序とbackpressure・重複除去・`AwaitRun` `InterruptRun`・全14 typed methodのrequestを設計例`native_requests.json`と照合）と、test binary自身を子processにした起動・停止の試験（環境・引数・作業directoryの隔離、異常exit、`Abort`と`Shutdown`の冪等・競合・kill段階）、**実binaryをbuildしてGateway double経由で動かす統合試験**（全method、replay・conflict・busy、`InterruptRun`→`AwaitRun`、`RunResume`、drain・cancelの`Shutdown`、`Abort`後の別processでのreplay）。
- **まだ無いもの**: CORE側の配線（`internal/adapter/nativeharnessclient`からの利用、ContextBlock revision・OriginProof署名の供給、Shiro profileの分岐。WP08後半）、Windows・Ubuntuでの実機検証（`GOOS=windows` `GOOS=linux`の`go vet`までは通る）。

Runが取り残されてもThreadは塞がらない。Threadの書込み権を新しいepochで取った時点で、旧epochの未終端Runが決定的に終端する（生成を送った記録があり終了の記録が無ければ`blocked / MODEL_GENERATION_OUTCOME_UNKNOWN`、無ければdeadline超過なら`incomplete / DEADLINE_EXCEEDED`、そうでなければ`incomplete / DRIVER_STOPPED`。いずれも`resumable=true`）。driverを持たない同processのRunはdeadline超過後の次の`turn/start`で`DEADLINE_EXCEEDED`として終端する。

Windowsの`internal/fsperm`は、同じfile handleから対象の種別・owner SID・DACLを読み、現在のprocess user SIDとownerの一致、およびnon-ownerへのallow ACEが無いことを確認する。新しいprivate directory component/fileはowner SIDを明示したprotected DACLで作り、rootにはfile・directory双方へのfull-control継承を設定する。既存ACLは確認だけを行い、修復しない。standalone CLIは起動時にprocess tokenのdefault ownerだけをTokenUser SIDへ合わせ、storageは一致しない埋込みprocessを変更せず書込み前に拒否する。Windows実機のstore smokeはP6Bに残る。`GOOS=windows`のbuild・`go vet`だけでは実機動作の受入にならない。

```sh
go build -o rencrow-harness ./cmd/rencrow-harness
```

`cmd/rencrow-harness`の試験は、使い捨てのconfigとdata rootで実行programを組み立て、`init`から`serve --stdio`までを子processとして往復する（COREもRenCrow_LLMも起動しない）。Runを実行する子process試験は、`internal/harnesstest`のGateway（Fakeをstrict wireでloopback HTTPへ出すもの）をconfigの`gateway.base_url`に指定して、実binaryが実clientで組み立てたproduction構成をそのまま通す。in-processのService試験は偽のModelPortを渡す。実Gateway・実Qwen・実機のRuntimeへの接続はしていない（WP09）。


`scripts/test-local.ps1`は検査の前に、tracked／untracked／ignored sourceを一度だけfresh private candidateへ固定する。除外するのは正確なroot `.git`と`Tmp`だけで、root `Tmp`にtracked fileがあればfail closedにする。`tmp`／`TMP`／`.GiT`などroot case variantもportable ambiguityとして拒む。nested `.git`／`Tmp`とignored fileはcandidateに含める。candidate manifestはrelative path・kind・size・SHA-256・portable modeを記録する。tracked regular fileのportable modeはGit indexの`100644`／`100755`を正本にする。Unixではworking treeのexecutable bitがindexと違う場合にrelative pathとmodeをmanifestへdirty inputとして記録し、Windowsではtracked fileのmodeをOS permissionから推測しない。untracked fileはUnixでworking treeのmodeを使い、Windowsではexec意図を推測せず`0644`を使う。Git index modeがcapture中に変化したらfail closedにする。このmode policy、source preparationの入力・consumer・failure actionは`test-local.plan.json`の各stepに記録する。source検査を行う五つのfixed stepは同じidentityを使い、`test-runtime-layout`はouter ownerのruntimeを検査する。fixed `go-test` stepは`go test ./... -count=1 -race -timeout=15m`を実行する。全体race gateがGoの既定10分を超えることが確認されているため、Go test自身には15分の上限を設定し、既存の3600秒step timeoutも維持する。`go test`はcandidate内でmodule rootの`repo_hygiene_test.go`も実行し、candidate外のmanifestも同じprivacy rulesでscanする（実path・private address・secretが無いことの検査）。candidate作成とguard成功は公開・archive作成を意味しない。

テストは`testdata/contract/`の設計vector（設計パッケージ由来のgolden）を読み、実装を独立に照合する。参照Python実装の出力で期待値を上書きしない。

## 設計資産の検査（Python）

`tools/speccheck/`のPythonは**設計文書・fixtureの検査専用**で、製品runtimeの依存ではない。

```sh
python -m pip install -r tools/speccheck/requirements.txt
python tools/speccheck/validate_package.py
python tools/speccheck/validate_contract_details.py
python tools/speccheck/validate_wire_contracts.py
```

検査はschema・DDL・例・対応表・合成vectorが対象で、製品は起動しない。全runtime試験は`not_run`のままである。

注意: 三つのscriptは実行のたびに`docs/DOCUMENT_VALIDATION.json` `docs/CONTRACT_VALIDATION.json` `docs/WIRE_CONTRACT_VALIDATION.json`を**上書きする**（設計パッケージ由来のfileで、書き換えない扱い）。実行するならrepositoryの複製の中で行う。このrepositoryの配置では、`migrations/001_initial.sql`に表`source_imports`とtriggerを足した（WP06 第2段）ため`DOCUMENT_VALIDATION.json`の`tables`が19→20、`local_document_links`が96→55になるのは数えるMarkdownの範囲の違い（このrepositoryでは`docs/*.md`だけ）、`all_json_syntax`が71→72になるのは初回の生成時には無かった`DOCUMENT_VALIDATION.json`自身を数えるためで、DDLの変更によるのは`tables`だけである。検査の判定はいずれも`passed`である。
